# 마인드스토리 제안서 워크벤치

기관 공고문·과업지시서·신청 양식을 분석하고, 확인된 마인드스토리 역량과 비교해 근거 추적이 가능한 사업계획서를 작성하는 Cloudflare Pages 애플리케이션입니다.

## 주요 기능

- 기존 5개 사업 유형 분류
- 원문 붙여넣기와 PDF/DOCX/TXT/HWPX 텍스트 추출 (HWP 바이너리는 변환 안내)
- 기관 요구사항·평가 기준·제출 항목 분석
- 「신청기관 정보」 다중 등록·선택과 항목별 `확인됨 / 확인 필요 / 오래된 정보` 구분
- 선택한 신청기관의 확인된 정보와 공고 요구 적합성 비교
- 부족 정보 확인 질문
- 근거 ID가 연결된 항목별 초안과 재작성
- 브라우저 자동 저장, 인쇄, PDF·DOCX 다운로드
- API 키가 없을 때 사실 생성을 피하는 로컬 규칙 분석 및 검토용 초안

## 로컬 실행

```powershell
npm install
npm run dev
```

로컬에서는 실제 OpenAI 키를 저장하거나 호출하지 않습니다. 정적 빌드 후 Cloudflare Pages 개발 서버를 실행하면 키가 없는 안전한 오류와 로컬 대체 흐름을 시험할 수 있습니다.

```powershell
npm run build
npm run cf:dev
```

## Cloudflare Pages 설정

- Build command: `npm run build`
- Build output directory: `dist`
- Root directory: 저장소 루트
- Production secret: `OPENAI_API_KEY`를 암호화된 Secret으로 등록
- Production variable: `OPENAI_MODEL`에 현재 계정에서 사용할 수 있는 모델 ID 등록
- Custom domain: `pro.ms12.org`

Cloudflare 대시보드의 Workers & Pages 프로젝트에서 Settings → Variables and Secrets에 API 키를 암호화된 Secret으로 등록합니다. 키를 로컬 파일, `index.html`, `.env`, `wrangler.toml` 또는 GitHub에 저장하지 마세요.

현재 코드는 설정 누락·입력 크기·출력 길이·단일 요청 타임아웃을 fail-closed 방식으로 처리합니다. 애플리케이션의 길이 제한과 타임아웃만으로 정확한 비용 상한이나 과금 취소가 보장되지는 않으므로, 공개 배포 전에는 운영 환경의 인증·요청 제한·예산 통제를 별도로 검토해야 합니다.

## 신청기관 정보

이 서비스는 여러 기관의 사업계획서를 대행 작성합니다. 공고를 분석하는 정보와 별도로, 상단 「신청기관 정보」 화면에서 신청기관을 여러 곳 등록·수정하고 작성 흐름 3단계(신청기관 선택)에서 이번 사업의 신청기관을 고릅니다. 마인드스토리도 등록기관 중 하나로만 취급합니다.

작성 흐름은 공고 가져오기 → 공고 확인 → 신청기관 선택(정보 불러오기·공고 대비 비교·부족 정보 질문) → 사업 선택·마스터 설계 → 계획서 작성 → 검토·완성 순서입니다.

- 마스터 설계와 계획서 작성 요청에는 `확인됨` 항목만 전달합니다. `확인 필요`·`오래된 정보`는 항목명과 상태만 전달하고 값은 전달하지 않습니다.
- 이번 사업 전용 값(예: 이번 공모 16회)은 신청기관 원본(예: 보유 12회)을 변경하지 않습니다.
- 신청기관 정보는 계획서 보관함과 같은 복구키(`X-Archive-Key`) 기준으로 D1 `applicant_organizations` 테이블에 보관합니다.

### 기관 문서에서 정보 추출

「신청기관 정보」에서 기관을 편집할 때 기존 사업계획서·결과보고서·기관소개서(PDF·DOCX·TXT 또는 붙여넣기)를 넣으면 규칙 기반(외부 AI 호출 없음)으로 「기관정보 업데이트 후보」를 만듭니다. 후보는 만들기만 하고 기관 정보를 자동으로 덮어쓰지 않습니다.

검증·코칭 결과 화면에서도 같은 방식으로 「이 계획서로 신청기관 정보 보강」을 실행할 수 있습니다. 검증에 사용한 계획서 원문에서 기관 기본정보·인력·프로그램·실적·성과·협력기관·시설·예산·성과측정 경험만 규칙 기반으로 뽑으며(추가 AI 호출 없음), 연락처·이메일·주민번호·생년월일이 포함된 문장은 후보로 만들지 않습니다.

- 후보 분류: `신규` / `동일` / `변경 가능성` / `충돌` / `누적 추가` / `이전 시점 정보`
- `동일` 후보를 반영하면 값·상태는 그대로 두고 해당 문서를 근거(출처)로만 추가합니다.
- 자료보관함에 저장된 과거 사업계획서는 다시 업로드하지 않고 「보관함 계획서 목록」에서 선택해 바로 후보를 만들 수 있습니다. 반영은 편집 중인 신청기관 한 곳에만 적용되고 D1 `applicant_organizations`에 저장되어 새로고침 후에도 남습니다.
- 편집 화면의 「출처별 정보」에서 어떤 문서에서 어떤 항목이 들어왔는지, 사업실적은 연도순으로 확인할 수 있습니다(기존 `source`·`asOf`·`history` 필드 재사용).
- 반영하면 항상 `확인 필요` 상태로 들어가며, 담당자가 확인한 뒤 `확인됨`으로 바꿉니다. 일괄 반영은 기존 값을 바꾸지 않는 `신규`·`누적 추가`만 처리합니다.
- 사업실적은 누적 정보이므로 최신값으로 덮어쓰지 않고 항목을 추가합니다.
- 항목별 `정보 기준시점(asOf)`을 두고, 값이 바뀌면 이전 값을 항목 이력에 남깁니다. 문서에 기준시점이 없으면 파일 업로드 날짜를 쓰지 않고 `기준시점 확인 필요`로 둡니다. 기존 정보보다 이전 시점 문서는 현재 값을 바꾸지 않고 이력으로만 남깁니다.

운영 배포 전에는 관리자가 D1 마이그레이션을 직접 적용해야 합니다.

```powershell
npx wrangler d1 migrations apply ms12-proposal-archive --remote
```

## 검증·코칭 자료 입력

- 평가받는 **사업계획서**는 클릭 선택과 드래그앤드롭 어느 쪽으로 넣어도 같은 처리 경로(`loadCoachingProposalFile`)를 사용합니다.
- **참고자료**(공고문·사업요강·평가기준·계획서 원본·기타)는 계획서와 분리해 여러 건 추가하며, 파일명과 자료유형을 구분해 검증 요청에 전달합니다. 계획서 본문에 합치지 않습니다.
- 참고자료는 검증 전에 로컬 규칙으로 먼저 판별합니다: `공식 근거로 사용 가능` / `관련 있으나 참고용` / `이번 사업과 맞지 않음` / `출처/진위 확인 필요` / `내용끼리 충돌함`. 연도·사업명·기관이 다른 자료와 출처를 확인할 수 없는 자료는 현재 공모의 공식 기준으로 사용하지 않으며, 확인할 수 없다고 해서 가짜로 단정하지 않습니다.
- 공식 근거로 판정된 자료끼리 총사업비·사업기간·마감 값이 어긋나면 `내용끼리 충돌함`으로 낮추고, 판정 사유를 입력 화면과 검증 결과 화면에 문장으로 표시합니다(예: “첨부한 2023년 사업요강은 현재 2026년 공모의 공식 기준으로 확인되지 않아 참고용으로만 사용했습니다.”).
- 코칭 정책에도 같은 규칙이 들어가며, 참고자료 원문은 근거 대조(evidence validation) 대상에 포함됩니다.

## 계획서 쓰기 ↔ 검증·코칭 왕복

「계획서 검증·코칭」은 심사자·수퍼바이저 역할만 하고 계획서를 직접 다시 쓰지 않습니다. 수정은 「계획서 쓰기」가 담당합니다.

1. 검증 결과의 개선 작업판에서 문제를 선택하고 「계획서 쓰기에서 수정」을 누르면 수정 위치·문제·이유·개선 방향·근거·확인 필요사항·변경 금지 확정값만 작성 화면으로 전달됩니다.
2. 계획서 작성 화면 상단의 수정 요청 목록에서 대상 항목을 지정하고 항목별로 직접 수정하거나 「이 항목 AI 수정」을 사용합니다. 확정값(인원·회기·기간·예산·성과 수치)이 바뀌면 수정안을 적용하지 않습니다.
3. 「수정본 버전 저장」은 이전 버전을 지우지 않고 V1, V2 … 로 누적하며 자료보관함에는 `revision-v{n}` 단계로 저장합니다. 각 버전은 언제든 되돌릴 수 있고, 되돌리기 전 작업본도 버전으로 남습니다.
4. 「다시 검증하기」는 수정본을 검증 화면으로 보내고 이전 결과를 유지하므로, 재검증에서 해결된 문제 / 남은 문제 / 새로 생긴 문제 / 개선 항목을 비교합니다.

외부에서 가져온 계획서도 같은 왕복을 사용합니다. 검증 결과 화면에서 「외부 계획서를 작업본으로 전환」을 누르면 업로드 원문을 항목 단위 작업본으로 나누고, 업로드 원본은 V1 「외부 원본」 버전에 원문 그대로 함께 보존합니다. 작성 중인 계획서 본문이 이미 있으면 전환하지 않고 기존 본문을 덮어쓰지 않습니다. 전환 후에는 문제 선택 → 계획서 쓰기에서 수정 → 새 버전 → 재검증이 내부 계획서와 동일하게 동작하며 확정값 보호 규칙도 같습니다.

내부 판정은 `제출 검토 완료 / 수정 후 재검토 / 작성 단계로 반려` 3단계입니다. 반려는 입력 근거에서 실제로 확인된 제출·자격·필수항목·예산·핵심 수치 문제에만 사용하며, 정보가 부족하다는 이유만으로 반려하지 않습니다. 공모기관의 선정·탈락 판정이 아니라 내부 품질관리 판정입니다.

## 한글 문서(HWP/HWPX) 처리

- **HWPX**는 브라우저에서 바로 읽습니다. OWPML은 XML을 담은 ZIP이므로 외부 변환 서비스나 추가 라이브러리 없이 표준 `DecompressionStream('deflate-raw')`으로 `Contents/section*.xml`을 풀어 문단·줄바꿈·표 칸 구분만 유지한 본문 텍스트를 추출합니다.
- **HWP(바이너리 5.0)**는 지원하지 않습니다. CFB 컨테이너 + 자체 레코드 구조이고 배포용 문서는 암호화되어 있어 브라우저에서 안정적으로 읽을 수 없습니다. 업로드하면 “한/글에서 [다른 이름으로 저장] → HWPX·PDF·DOCX로 저장해 다시 올려 주세요”라고 안내합니다.
- 적용 위치: 계획서 검증·코칭 업로드, 신청기관 문서 추출, 공고문·신청서 업로드, 직접 자료 추가.

## 현재 데이터 제한

초기 기관 정보는 `mindstory.kr`에서 공개 확인 가능한 프로그램과 검사만 포함합니다. 인력·자격·실적·예산·시설·보험 등은 증빙 자료가 제공되기 전까지 `확인 필요`로 처리합니다. 네이버 블로그는 자동 접근 제한으로 개별 게시물을 초기 데이터에 반영하지 않았습니다.
