# 마인드스토리 제안서 워크벤치

기관 공고문·과업지시서·신청 양식을 분석하고, 확인된 마인드스토리 역량과 비교해 근거 추적이 가능한 사업계획서를 작성하는 Cloudflare Pages 애플리케이션입니다.

## 주요 기능

- 기존 5개 사업 유형 분류
- 원문 붙여넣기와 PDF/DOCX/TXT/HWPX 텍스트 추출 (HWP 바이너리는 변환 안내)
- 기관 요구사항·평가 기준·제출 항목 분석
- 「신청기관 정보」 다중 등록·선택과 항목별 `확인됨 / 확인 필요 / 오래된 정보` 구분
- 선택한 신청기관의 확인된 정보와 공고 요구 적합성 비교
- 부족 정보 확인 질문
- 근거 ID가 연결된 항목별 초안과 재작성
- 브라우저 자동 저장, 인쇄, PDF·DOCX 다운로드
- API 키가 없을 때 사실 생성을 피하는 로컬 규칙 분석 및 검토용 초안

## 로컬 실행

```powershell
npm install
npm run dev
```

로컬에서는 실제 OpenAI 키를 저장하거나 호출하지 않습니다. 정적 빌드 후 Cloudflare Pages 개발 서버를 실행하면 키가 없는 안전한 오류와 로컬 대체 흐름을 시험할 수 있습니다.

```powershell
npm run build
npm run cf:dev
```

## Cloudflare Pages 설정

- Build command: `npm run build`
- Build output directory: `dist`
- Root directory: 저장소 루트
- Production secret: `OPENAI_API_KEY`를 암호화된 Secret으로 등록
- Production variable: `OPENAI_MODEL`에 현재 계정에서 사용할 수 있는 모델 ID 등록
- Custom domain: `pro.ms12.org`

Cloudflare 대시보드의 Workers & Pages 프로젝트에서 Settings → Variables and Secrets에 API 키를 암호화된 Secret으로 등록합니다. 키를 로컬 파일, `index.html`, `.env`, `wrangler.toml` 또는 GitHub에 저장하지 마세요.

현재 코드는 설정 누락·입력 크기·출력 길이·단일 요청 타임아웃을 fail-closed 방식으로 처리합니다. 애플리케이션의 길이 제한과 타임아웃만으로 정확한 비용 상한이나 과금 취소가 보장되지는 않으므로, 공개 배포 전에는 운영 환경의 인증·요청 제한·예산 통제를 별도로 검토해야 합니다.

## 신청기관 정보

이 서비스는 여러 기관의 사업계획서를 대행 작성합니다. 공고를 분석하는 정보와 별도로, 상단 「신청기관 정보」 화면에서 신청기관을 여러 곳 등록·수정하고 작성 흐름 3단계(신청기관 선택)에서 이번 사업의 신청기관을 고릅니다. 마인드스토리도 등록기관 중 하나로만 취급합니다.

작성 흐름은 공고 가져오기 → 공고 확인 → 신청기관 선택(정보 불러오기·공고 대비 비교·부족 정보 질문) → 사업 선택·마스터 설계 → 계획서 작성 → 검토·완성 순서입니다.

- 마스터 설계와 계획서 작성 요청에는 `확인됨` 항목만 전달합니다. `확인 필요`·`오래된 정보`는 항목명과 상태만 전달하고 값은 전달하지 않습니다.
- 이번 사업 전용 값(예: 이번 공모 16회)은 신청기관 원본(예: 보유 12회)을 변경하지 않습니다.
- 신청기관 정보는 계획서 보관함과 같은 복구키(`X-Archive-Key`) 기준으로 D1 `applicant_organizations` 테이블에 보관합니다.

### 기관 문서에서 정보 추출

「신청기관 정보」에서 기관을 편집할 때 기존 사업계획서·결과보고서·기관소개서(PDF·DOCX·TXT 또는 붙여넣기)를 넣으면 규칙 기반(외부 AI 호출 없음)으로 「기관정보 업데이트 후보」를 만듭니다. 후보는 만들기만 하고 기관 정보를 자동으로 덮어쓰지 않습니다.

검증·코칭 결과 화면에서도 같은 방식으로 「이 계획서로 신청기관 정보 보강」을 실행할 수 있습니다. 검증에 사용한 계획서 원문에서 기관 기본정보·인력·프로그램·실적·성과·협력기관·시설·예산·성과측정 경험만 규칙 기반으로 뽑으며(추가 AI 호출 없음), 연락처·이메일·주민번호·생년월일이 포함된 문장은 후보로 만들지 않습니다.

- 후보 분류: `신규` / `동일` / `변경 가능성` / `충돌` / `누적 추가` / `이전 시점 정보`
- `동일` 후보를 반영하면 값·상태는 그대로 두고 해당 문서를 근거(출처)로만 추가합니다.
- 자료보관함에 저장된 과거 사업계획서는 다시 업로드하지 않고 「보관함 계획서 목록」에서 선택해 바로 후보를 만들 수 있습니다. 반영은 편집 중인 신청기관 한 곳에만 적용되고 D1 `applicant_organizations`에 저장되어 새로고침 후에도 남습니다.
- 편집 화면의 「출처별 정보」에서 어떤 문서에서 어떤 항목이 들어왔는지, 사업실적은 연도순으로 확인할 수 있습니다(기존 `source`·`asOf`·`history` 필드 재사용).
- 반영하면 항상 `확인 필요` 상태로 들어가며, 담당자가 확인한 뒤 `확인됨`으로 바꿉니다. 일괄 반영은 기존 값을 바꾸지 않는 `신규`·`누적 추가`만 처리합니다.
- 사업실적은 누적 정보이므로 최신값으로 덮어쓰지 않고 항목을 추가합니다.
- 항목별 `정보 기준시점(asOf)`을 두고, 값이 바뀌면 이전 값을 항목 이력에 남깁니다. 문서에 기준시점이 없으면 파일 업로드 날짜를 쓰지 않고 `기준시점 확인 필요`로 둡니다. 기존 정보보다 이전 시점 문서는 현재 값을 바꾸지 않고 이력으로만 남깁니다.

운영 배포 전에는 관리자가 D1 마이그레이션을 직접 적용해야 합니다.

```powershell
npx wrangler d1 migrations apply ms12-proposal-archive --remote
```

## 공개 소개 화면

`pro.ms12.org`에 로그아웃 상태로 들어오면 로그인 창이 아니라 **서비스 소개 화면**(`landingView()`)이 먼저 열립니다. 핵심 가치 · 이용 흐름(6단계) · 주요 기능 · 이용 대상 · 보안·승인 안내와 「무료로 시작하기」·「로그인」 버튼으로 이루어집니다.

- 화면 갈림은 `auth.view`(`'landing' | 'auth'`) 한 값과 `showAuthForm()`으로만 정합니다. 새 라우터나 URL 경로는 없습니다.
- 소개 화면은 **서버를 부르지 않고 저장된 작업 상태도 읽지 않습니다.** 공용 컴퓨터에서 앞사람의 사업명이 남지 않게 하려는 것입니다.
- 「무료로 시작하기」·「로그인」을 누르면 기존 로그인/회원가입 화면으로 넘어가고, 그 화면의 「← 서비스 소개」로 되돌아옵니다.
- 로그인한 사람(관리자·운영관리자·승인 회원)은 소개 화면을 거치지 않고 곧바로 기존 화면으로 갑니다. 승인 대기 회원은 지금처럼 가입 정보 입력 화면을 봅니다.
- 오류·안내 문구가 있으면(소셜 로그인 실패, 로그아웃, 세션 만료, 복구코드 완료) 소개가 아니라 로그인 화면에 띄웁니다. Google·카카오 콜백 주소로 돌아온 경우도 첫 화면부터 로그인 화면입니다.
- 스타일은 이미 있던 `.landing-*` 규칙을 그대로 씁니다(CSS 추가 없음).

## 공모정보 검색 (비회원 공개)

로그인 없이 `/api/public`으로 열린다. **이미 D1에 모아 둔 `archived_notices`만 읽으며 AI도 외부 API도 부르지 않고, 이 기능이 새로 수집하지도 않는다.** 사용자 화면에서는 「크롤링」이라는 말을 쓰지 않고 「공모정보 검색」으로만 부른다.

### 두 가지 검색 범위

| 방식 | 보는 곳 |
|---|---|
| **맞춤검색** (기본) | 공고 제목 + 제목에 연결된 연관 키워드 |
| **광역검색** | 맞춤검색 범위 + 공고 요약 내용 |

「연관 키워드」는 제목의 낱말, 제목에서 확인된 지역·대상·분야와 그 다른 이름(아동↔어린이, 노인↔어르신 등), 주최기관이다. **공고 본문 원문(`notice_json`)은 어느 방식에도 들어가지 않으며 SELECT에도 없다.**

결과 순위는 **제목 전체 일치 → 제목 포함 → 연관 키워드 일치 → 요약 내용 일치**다. 등급이 세부 점수보다 항상 먼저라, 광역검색에서도 제목에 걸린 결과가 요약만 걸린 결과보다 위에 온다. 결과마다 어느 등급으로 걸렸는지(`matchedBy`)를 함께 보여 준다.

검색어는 띄어쓰기·대소문자·특수문자 차이를 정규화하고(`normalizeText`/`compactText`), 띄어쓰기를 지운 형태로 비교해 「가족 기능」으로도 「가족기능」을 찾는다. 여러 낱말을 넣으면 모두 걸리는 자료만 남는다.

필터는 **모집 중·마감 임박(7일 이내)·마감 / 지역 / 대상 / 분야 / 주최기관**이며, 후보 값은 실제 자료에서 센 것만 보여 준다.

### 왜 FTS5를 쓰지 않았나

2,000행으로 실측한 결과다.

| 검색어 | 부분일치 | FTS5 unicode61 | FTS5 trigram |
|---|---|---|---|
| 기금 | 400건 | 0건 | 0건 |
| 아동 | 800건 | 0건 | 0건 |
| 가족기능 | 667건 | 667건 | 667건 |

한국어는 「복권기금」처럼 한 낱말이 한 토큰이라 unicode61은 그 안의 「기금」을 찾지 못하고, trigram은 세 글자 미만 검색어를 아예 받지 못한다. **두 글자 검색어가 가장 흔한 우리 자료에서는 두 방식 모두 결과가 0이 된다.** 같은 조건에서 부분일치는 0.5~1.6ms였고 현재 수집 규모는 수십 건이므로, 정규화한 검색 문자열에 부분일치를 걸고 서버가 순위를 매기는 방식이 맞다. 수천 건을 넘어가면 `search_title`·`search_keywords`·`search_summary` 열로 SQL 단계에서 먼저 좁히면 된다(열은 이미 만들어 두었다).

### 비회원에게 보이는 것

요약 · 지원대상 · 접수기간 · 지원금액 · 원문 출처와, 목록에 필요한 제목 · 주최기관 · 마감 상태 · 분류 표시뿐이다. 개인정보, 내부 검토자료, 회원 계획서(`archived_proposals`), 기관별 분석자료(`applicant_organizations`)는 이 경로에서 **읽지 않는다** — 테스트가 이 경로의 SQL이 `archived_notices` 하나만 참조하는지 확인한다. 상세 적합성 분석과 맞춤 사업설계는 회원가입으로 안내한다.

### 관리자 공모정보 관리

`/api/admin` `listNotices`로 공개 여부와 무관하게 전체 수집자료를 검색하고, **출처 URL · 수집일 · 최종 확인일 · 중복 여부 · 공개 여부**를 함께 본다. 중복은 내용 해시가 같거나 제목(띄어쓰기 무시)과 마감일이 같은 다른 자료로 판정한다. `setNoticePublic`으로 공개 여부를 바꾸면 비회원 검색 결과가 즉시 따라 바뀌고 감사기록이 남는다.

## 이용권과 비용 통제

생성 API는 돈이 든다. 그래서 **계정 단위 이용권(`users.plan`)** 으로 통제하며, 화면이 아니라 서버가 막는다(`server/plan.js`).

| 이용권 | 누구 | 쓸 수 있는 것 |
|---|---|---|
| `full` | 관리자·운영관리자(역할로 자동), 관리자가 부여한 회원, **마이그레이션 시점의 기존 활성 회원** | 전체 기능 |
| `trial` | 신규 가입 회원(기본값) | **MS12 핵심제안서 계정당 1회**만 |

### MS12 핵심제안서

무료 회원이 쓸 수 있는 유일한 생성 기능이다. 공모사업 전체 계획서와는 다른 기능으로, **제안서 한 부**를 조건에 맞춰 완성한다.

**1단계 · 제안 조건** — 제안자·기관 기본정보, 핵심 아이디어(필수·20자 이상), 제안 목적, 제출처 유형, 실제 제출기관명(선택), 희망 페이지 수(1~20쪽)를 받는다. 참고 자료 붙여넣기는 선택이다.

**제출처에 따라 구성이 달라진다.** 같은 아이디어·같은 쪽수여도 항목 이름과 순서가 바뀐다.

| 제출처 | 앞세우는 것 |
|---|---|
| 관공서·공공기관 | 공익성 · 정책 연계 · 실행체계 · 예산 · 성과 |
| 기업 | 기대효과 · 차별성 · 비용 대비 가치 · 협력방식 |
| 재단·복지기관 | 대상자의 필요 · 사회적 가치 · 성과 · 지속가능성 |
| 학교·교육기관 | 대상 · 교육목표 · 운영과정 · 안전 · 기대효과 |
| 내부보고 | 필요성 · 효율성 · 실행 가능성 · 의사결정 요청 |
| 기타 | 사용자가 적은 목적과 받는 사람 기준 |

**쪽수에 따라 항목 수와 분량이 달라진다.** 쪽당 본문 1,400자를 기준으로 삼는다.

| 쪽 | 항목 | 본문 | 표 |
|---|---|---|---|
| 1 | 4개 | 1,400자 | 0 |
| 3 | 7개 | 4,199자 | 2 |
| 5 | 9개 | 6,999자 | 3 |
| 7 | 11개 | 9,800자 | 3 |
| 10 | 12개 | 14,002자 | 3 |

짧으면 의사결정에 먼저 필요한 항목(개요·필요성·핵심 내용·기대효과)만 남기고, 길면 활동·일정·역할·예산 방향·성과지표·위험 대응까지 차례로 펼친다. **분량을 채우려고 같은 말을 반복하지 않는다** — 프롬프트가 반복·늘려 쓰기·앞 항목 옮겨 적기를 금지하고, 쓸 내용이 모자라면 짧게 끝내고 확인 필요로 남기게 한다.

**구성안을 먼저, 본문을 나중에.** 스키마에서 `outline`이 `sections`보다 앞에 있어 모델이 페이지별 구성안을 확정한 뒤 본문을 이어 쓴다. 서버는 받은 본문을 구성안에 다시 맞춘다(`alignSections`) — 모델이 항목을 빠뜨리거나 쪽 번호를 흔들어도 화면·출력이 흔들리지 않고, 채우지 못한 항목은 지어내지 않고 [확인 필요]로 남는다.

**미리보기와 출력이 같은 쪽 나눔을 쓴다.** 화면은 쪽별로 묶어 보여 주고, DOCX·PDF는 구성안이 정한 자리에서만 쪽을 넘긴다(`pageBreaks`). **글자 크기와 여백은 줄이지 않는다** — 쪽수는 내용의 양으로 맞춘다.

**안전장치는 그대로다.** 계정당 1회 제한(`users.trial_used_at` 조건부 갱신), 실패 시 기회 반환, 사용량·비용 기록, 계획서·계정 상한이 모두 이 기능에도 걸린다. 출력 토큰 상한은 쪽수를 따른다(1,200 + 쪽 × 1,600, 최대 16,000).

### 서버에서 막는 것 (화면에서 숨기는 것이 아니다)

| 경로 | 무료 체험 계정 |
|---|---|
| `/api/proposal` `analyze` `master` `draft` `draftPart` `fullProposal` `preciseReview` `patchSections` `rewrite` `finalize` | 403 `needsPlan` |
| `/api/proposal-coaching` (probe 제외) | 403 |
| `/api/proposal-review` | 403 |
| `/api/archive` `saveProposal` | 403 |

DOCX·PDF·ZIP 출력은 브라우저에서만 이루어지고 별도의 서버 경로가 없다. **공모사업 전체 계획서**의 본문은 위 API로만 만들어지므로, API를 막는 것이 곧 그 출력을 막는 것이다. 무료 회원에게는 그 작업 화면 자체가 열리지 않는다.

다만 **자기가 만든 핵심제안서는 내려받을 수 있다.** 자기 계정으로 한 번 만든 결과물이라 막을 이유가 없고, 목표 쪽수에 맞춘 출력이 이 기능의 일부다. 제출용 ZIP 묶음과 전체 계획서 출력은 그대로 전체 이용권 기능이다.

### 부여·회수

- **관리자만** `/api/admin` `setPlan`으로 `full`/`trial`을 바꾼다. `admin` 역할은 이 경로로 줄 수 없다.
- 이용권은 요청마다 `users` 행에서 다시 읽으므로 바꾸면 다시 로그인하지 않아도 즉시 반영된다.
- **운영관리자는 조회만 한다.** `/api/operator`에서 `setPlan`·`grantFullPlan`·`revokeFullPlan`·`resetTrial`은 403으로 거절되고 그 시도까지 감사기록에 남는다.

### 결제

결제 기능은 만들지 않았다. 전체 이용권이 없는 사용자에게는 금액·결제수단을 보여 주지 않고 **「이용권 문의」** 로만 안내한다(`CONTACT_LABEL`).

## AI 사용량·비용 기록

OpenAI를 부르는 세 경로(`/api/proposal`, `/api/proposal-coaching`, `/api/proposal-review`)가 호출마다 `ai_usage_events`에 한 줄을 남긴다. **성공·실패를 가리지 않는다** — 실패한 호출에도 토큰이 청구될 수 있기 때문이다. 기록이 실패해도 생성 자체는 막지 않는다.

### 남기는 것과 남기지 않는 것

| 남긴다 | 남기지 않는다 |
|---|---|
| 모델명, 작업 종류(`analyze`·`fullProposal`·`coaching:start`·`review` 등) | 공고문·계획서 원문 |
| 입력·캐시·출력·추론·합계 토큰 | 프롬프트, 응답 본문 |
| 비용(마이크로달러), 단가 설정 여부 | API 키 |
| 처리시간, 성공 여부, 짧은 실패 코드 | 오류 문장 |
| 회원 식별자·로그인 이메일, 계획서 식별자 | 계획서 제목·내용 |

`cached_input_tokens`는 `input_tokens`의 일부이고 `reasoning_tokens`는 `output_tokens`에 포함된 값이라 겹쳐 세지 않는다. 비용은 `(입력 − 캐시) × 입력단가 + 캐시 × 캐시단가 + 출력 × 출력단가`이며, 부동소수 오차 없이 더할 수 있도록 **마이크로달러(USD × 1,000,000) 정수**로 저장한다.

### 단가 설정

단가는 Cloudflare 환경변수로 넣는다(1M 토큰당 USD).

| 이름 | 필수 |
|---|---|
| `OPENAI_PRICE_INPUT_PER_MTOK` | 비용 계산에 필요 |
| `OPENAI_PRICE_OUTPUT_PER_MTOK` | 비용 계산에 필요 |
| `OPENAI_PRICE_CACHED_INPUT_PER_MTOK` | 선택(없으면 입력 단가와 같게 본다) |

**단가를 넣지 않으면 비용을 0으로 지어내지 않는다.** 토큰만 기록하고 `priced = 0`으로 남기며, 화면은 「단가 미설정」이라고 알린다. 0달러를 「무료」로 오해하지 않게 하기 위해서다.

### 경고와 강제 상한

계획서 한 건과 계정 하루에 상한을 건다. 상한의 **70%를 넘으면 경고**, **100%에 닿으면 서버가 다음 호출을 거절**한다(403 `capReached`). 막힌 요청은 OpenAI를 부르지 않으므로 비용이 더 늘지 않는다.

| 환경변수 | 기본값 |
|---|---|
| `AI_PROPOSAL_COST_CAP_USD` | 20 |
| `AI_PROPOSAL_TOKEN_CAP` | 2,000,000 |
| `AI_USER_DAILY_TOKEN_CAP` | 6,000,000 |

**비용 상한과 토큰 상한을 함께 둔 이유**: 단가를 넣지 않으면 비용이 0이라 비용 상한만으로는 상한이 꺼진 것과 같아진다. 토큰 상한은 단가와 무관하게 언제나 동작한다.

계획서 식별자는 화면이 보내 준다. 비워 보내면 계획서 단위로 묶이지 않으므로 **계정 하루 상한**이 대신 막는다.

### 보는 곳

관리자는 관리자 화면의 「AI 사용량·비용」, 운영관리자는 운영 화면의 같은 탭에서 본다. 기간(7·30·90일)을 고르면 **총계 · 회원별 · 계획서별 · 작업 종류별 · 날짜별**로 나뉘어 나온다. 운영관리자는 **읽기만** 하며 `setUsageCap`·`setPricing`은 서버가 거절하고 그 시도까지 감사기록에 남는다.

## 공개 예시 계획서

로그인 없이 랜딩에서 「우수 계획서 예시 보기」로 열 수 있다(`src/example-plan.js`). 정적 문자열만 그리며 **API를 한 번도 부르지 않는다.** 가상의 사례이고 기관명은 「○○기관」으로만 적어 개인정보와 실제 기관정보가 들어 있지 않다.

## 관리자 포털 · 계획서 포털

관리자·운영관리자는 **계정을 따로 만들지 않고 한 계정으로 두 포털을 오갑니다.** 로그인하면 먼저 어느 쪽으로 들어갈지 고르고, 들어간 뒤에도 위쪽 단추로 언제든 바꿉니다.

| 포털 | 무엇을 하나 |
|---|---|
| **계획서 포털** | 회원이 보는 화면 그대로 들어가 직접 계획서를 작성합니다. 공고 분석 → 신청기관 → 설계 → 작성 → 검증 → 제출본까지 회원과 같은 흐름입니다. |
| **관리자 포털** | 관리자 입장에서 회원 승인·중지·역할, 이용권 부여·회수, AI 사용량·비용, 공모정보 공개를 관리합니다. |

- 고른 포털은 작업 상태와 함께 저장되어 새로고침해도 남습니다(`state.portal`). 알 수 없는 값이면 다시 고르게 합니다.
- **계획서 포털에서는 관리 화면이 열리지 않습니다.** 저장된 화면 위치가 `admin`·`operator`여도 홈으로 되돌립니다. 회원이 보는 화면과 같게 하려는 것이라, 관리 진입점 대신 「관리자 포털」 단추 하나만 남습니다.
- 관리자 포털에서는 「관리자」·「운영관리자」 진입점과 「계획서 포털」 단추가 함께 나옵니다. 관리·운영 화면의 「계획서 포털로」도 같은 전환을 씁니다.
- 포털은 화면 전환일 뿐 **권한 차단을 대신하지 않습니다.** 역할 가드(`activeTool === 'admin' && !isAdmin()`)와 서버 차단은 그대로입니다. 승인 대기·무료 체험 회원 흐름이 포털보다 먼저 걸립니다.
- 일반 회원에게는 포털이 없습니다. 지금처럼 작업 화면 하나만 봅니다.

## 역할과 운영관리자(operator)

계정 역할은 `admin`(관리자) · `operator`(운영관리자) · `customer`(고객) 세 가지입니다. 화면에서 숨기는 것이 아니라 서버(`functions/api/*`)에서 실제로 막습니다.

| 하는 일 | admin | operator | 근거 |
|---|---|---|---|
| 회원 승인·중지·재활성화 | O | O | `/api/operator` |
| 회원 검색(이름·이메일·기관명·연락처·식별자) | O | O | `/api/operator` `overview` |
| 이용 흔적(세션 수·최근 활동)·로그인 잠금 상태 확인 | O | O | `sessions` · `login_attempts` |
| 멈춘 작업 단계·최근 오류 확인 | O | O | `user_activity_events` |
| 로그인 잠금 해제 / 전체 세션 종료 | O | O | `/api/operator` |
| 일회용 계정 복구코드 발급 | O | O | `account_recovery_codes` |
| 이용권(전체/무료 체험) 조회 | O | O | `/api/operator` `overview` |
| 운영관리자 지정·해제 | O | **X** | `/api/admin` `setRole` (admin 전용) |
| 전체 이용권 부여·회수 | O | **X** | `/api/admin` `setPlan` (admin 전용) |
| 계정·자료 영구 삭제, 전체 내보내기 | O(삭제만) | **X** | `/api/admin` `deleteUser` |
| 비밀번호 조회·직접 지정, 요금·상품·결제정책, 환불, API 키·모델·시스템 설정, 관리자 계정 변경 | X | **X** | 어느 경로에도 기능이 없음 |

- 운영관리자 권한 밖 동작(`setRole`·`refund`·`setPricing`·`setApiKey`·`deleteUser`·`exportAll`·`changeAdmin` 등)은 `/api/operator`에서 403으로 거절하고 그 시도까지 감사기록에 남깁니다(`server/operator-scope.js`).
- 운영관리자는 관리자 계정·다른 운영관리자 계정·자기 계정을 대상으로 삼을 수 없습니다.
- 관리자 계정은 화면에서 만들 수 없습니다. `node scripts/create-admin.mjs` 로만 만듭니다.

### 계정 복구코드

- 운영관리자가 발급하면 `ABCD-EFGH-JKMN` 형식의 코드가 **응답에 한 번만** 실립니다. D1에는 SHA-256 해시만 남고 원문·비밀번호는 어디에도 저장되지 않습니다.
- **10분 유효 · 1회 사용**입니다. 새로 발급하면 그 계정의 이전 코드는 폐기됩니다. 중지된 계정에는 발급하지 않습니다.
- 사용자는 로그인 화면의 「복구코드」 탭에서 이메일·코드·새 비밀번호를 넣어 **본인이 직접** 비밀번호를 정합니다. 운영관리자는 비밀번호를 보거나 대신 정할 수 없습니다.
- 새 비밀번호를 정하면 그 계정의 **기존 세션 전부와 남은 복구코드 전부**를 폐기하고 로그인 실패 기록을 지웁니다.

### 감사기록

승인·중지·재활성화·잠금 해제·세션 종료·복구코드 발급·복구코드 사용과 거절된 시도까지 `admin_audit_log`에 실행자(계정·역할)·대상·동작·결과·시각·짧은 사유를 남깁니다. 계획서 원문·비밀번호·복구코드 값은 남기지 않습니다.

### 아직 연결되지 않은 항목 (값을 만들어 보여 주지 않음)

| 항목 | 이유 |
|---|---|
| 결제금액 · 결제상태 | 결제 기능이 연결되어 있지 않아 저장된 자료가 없습니다. |
| 이용기간 | 구독·이용기간을 저장하는 곳이 없습니다. 가입일과 계정 상태만 확인합니다. |
| 이용량(작성·검증 건수) | 계획서·신청기관 자료는 브라우저 복구키(`X-Archive-Key`) 기준으로 보관되어 계정과 연결되지 않습니다. |

운영 화면은 이 항목들을 `미연동`으로 표시하고 사유를 함께 보여 줍니다.

### 진행·오류 기록

`/api/activity`는 **작업 단계 번호와 미리 정한 오류 코드만** 받습니다(`server/activity.js`). 계획서 원문·입력값·오류 문장은 브라우저에서 보내지 않고 `ai:timeout`·`server:500` 같은 코드로 바꿔 보냅니다. 규칙에 맞지 않는 값은 `unknown`으로 저장하며, 계정당 최근 40건만 남습니다. 문제 확인 화면에도 단계 번호·오류 코드·시각만 표시합니다.

## 검증·코칭 자료 입력

- 평가받는 **사업계획서**는 클릭 선택과 드래그앤드롭 어느 쪽으로 넣어도 같은 처리 경로(`loadCoachingProposalFile`)를 사용합니다.
- **참고자료**(공고문·사업요강·평가기준·계획서 원본·기타)는 계획서와 분리해 여러 건 추가하며, 파일명과 자료유형을 구분해 검증 요청에 전달합니다. 계획서 본문에 합치지 않습니다.
- 참고자료는 검증 전에 로컬 규칙으로 먼저 판별합니다: `공식 근거로 사용 가능` / `관련 있으나 참고용` / `이번 사업과 맞지 않음` / `출처/진위 확인 필요` / `내용끼리 충돌함`. 연도·사업명·기관이 다른 자료와 출처를 확인할 수 없는 자료는 현재 공모의 공식 기준으로 사용하지 않으며, 확인할 수 없다고 해서 가짜로 단정하지 않습니다.
- 공식 근거로 판정된 자료끼리 총사업비·사업기간·마감 값이 어긋나면 `내용끼리 충돌함`으로 낮추고, 판정 사유를 입력 화면과 검증 결과 화면에 문장으로 표시합니다(예: “첨부한 2023년 사업요강은 현재 2026년 공모의 공식 기준으로 확인되지 않아 참고용으로만 사용했습니다.”).
- 코칭 정책에도 같은 규칙이 들어가며, 참고자료 원문은 근거 대조(evidence validation) 대상에 포함됩니다.

## 계획서 원문 구조 분석과 수정본 재가공

검증·코칭 화면의 「원문 구조 분석」은 AI 호출 없이 규칙만으로 동작합니다.

1. **무엇을 읽었는지 보여줍니다** — 원문 글자수·줄수·문단수·인식한 제목 수를 표시하고, PDF·HWPX 추출 과정에서 제목이나 문단이 무너졌으면 경고합니다. 줄바꿈이 사라진 문서는 문서 안의 번호 제목 앞에서 끊어 분석 기준점을 만듭니다(글자는 지우지 않습니다).
2. **14개 항목으로 구조화합니다** — 사업명, 목적, 필요성, 대상·인원, 세부 프로그램, 기간·일정·회기, 수행 인력, 신청기관 역량, 협력기관, 예산, 성과목표, 성과지표·측정, 기대효과, 공고 요구·평가기준 대응. 없는 항목은 만들지 않고 `없음`·`확인 필요`로 두며, 항목마다 원문 위치와 근거 문장을 함께 남깁니다.
3. **심사형 분석** — 항목마다 `현재 내용 → 문제점 → 심사에서 불리한 이유 → 근거 → 보완 방향 → 수정 문장` 순으로 정리하고, `필요성 → 대상 → 프로그램 → 예산 → 성과목표 → 성과지표` 연결과 인원·회기·예산 수치 일관성을 점검합니다. 서로 다른 위치에서 값이 어긋날 때만 `최우선 경고`로 보고, 한 곳에서 여러 값이 나오면 `확인 필요`로 둡니다.
4. **수정본(V2) 재가공** — 문제를 고르거나 「주요 문제 전체 선택」 후 수정본을 만들면, 문제가 연결된 문단에만 `[보완안]` 문장을 덧붙이고 나머지 문단은 그대로 둡니다. V1 원본은 버전으로 보존되고, 확정 수치는 바꾸지 않으며 계산으로 얻은 진단 수치는 본문에 넣지 않습니다. 이후 기존 왕복 구조(수정 요청 목록 → 항목별 수정 → 다시 검증)로 이어집니다.

## 계획서 쓰기 ↔ 검증·코칭 왕복

「계획서 검증·코칭」은 심사자·수퍼바이저 역할만 하고 계획서를 직접 다시 쓰지 않습니다. 수정은 「계획서 쓰기」가 담당합니다.

1. 검증 결과의 개선 작업판에서 문제를 선택하고 「계획서 쓰기에서 수정」을 누르면 수정 위치·문제·이유·개선 방향·근거·확인 필요사항·변경 금지 확정값만 작성 화면으로 전달됩니다.
2. 계획서 작성 화면 상단의 수정 요청 목록에서 대상 항목을 지정하고 항목별로 직접 수정하거나 「이 항목 AI 수정」을 사용합니다. 확정값(인원·회기·기간·예산·성과 수치)이 바뀌면 수정안을 적용하지 않습니다.
3. 「수정본 버전 저장」은 이전 버전을 지우지 않고 V1, V2 … 로 누적하며 자료보관함에는 `revision-v{n}` 단계로 저장합니다. 각 버전은 언제든 되돌릴 수 있고, 되돌리기 전 작업본도 버전으로 남습니다.
4. 「다시 검증하기」는 수정본을 검증 화면으로 보내고 이전 결과를 유지하므로, 재검증에서 해결된 문제 / 남은 문제 / 새로 생긴 문제 / 개선 항목을 비교합니다.

외부에서 가져온 계획서도 같은 왕복을 사용합니다. 검증 결과 화면에서 「외부 계획서를 작업본으로 전환」을 누르면 업로드 원문을 항목 단위 작업본으로 나누고, 업로드 원본은 V1 「외부 원본」 버전에 원문 그대로 함께 보존합니다. 작성 중인 계획서 본문이 이미 있으면 전환하지 않고 기존 본문을 덮어쓰지 않습니다. 전환 후에는 문제 선택 → 계획서 쓰기에서 수정 → 새 버전 → 재검증이 내부 계획서와 동일하게 동작하며 확정값 보호 규칙도 같습니다.

내부 판정은 `제출 검토 완료 / 수정 후 재검토 / 작성 단계로 반려` 3단계입니다. 반려는 입력 근거에서 실제로 확인된 제출·자격·필수항목·예산·핵심 수치 문제에만 사용하며, 정보가 부족하다는 이유만으로 반려하지 않습니다. 공모기관의 선정·탈락 판정이 아니라 내부 품질관리 판정입니다.

## 한글 문서(HWP/HWPX) 처리

- **HWPX**는 브라우저에서 바로 읽습니다. OWPML은 XML을 담은 ZIP이므로 외부 변환 서비스나 추가 라이브러리 없이 표준 `DecompressionStream('deflate-raw')`으로 `Contents/section*.xml`을 풀어 문단·줄바꿈·표 칸 구분만 유지한 본문 텍스트를 추출합니다.
- **HWP(바이너리 5.0)**는 지원하지 않습니다. CFB 컨테이너 + 자체 레코드 구조이고 배포용 문서는 암호화되어 있어 브라우저에서 안정적으로 읽을 수 없습니다. 업로드하면 “한/글에서 [다른 이름으로 저장] → HWPX·PDF·DOCX로 저장해 다시 올려 주세요”라고 안내합니다.
- 적용 위치: 계획서 검증·코칭 업로드, 신청기관 문서 추출, 공고문·신청서 업로드, 직접 자료 추가.

## 현재 데이터 제한

초기 기관 정보는 `mindstory.kr`에서 공개 확인 가능한 프로그램과 검사만 포함합니다. 인력·자격·실적·예산·시설·보험 등은 증빙 자료가 제공되기 전까지 `확인 필요`로 처리합니다. 네이버 블로그는 자동 접근 제한으로 개별 게시물을 초기 데이터에 반영하지 않았습니다.
