## 5. 프롬프트 캐싱 — **거의 안 걸립니다 (실측 2.9%)**

134건 실측에서 캐시된 입력은 전체 입력 1,282,961토큰 중 **36,757토큰(2.9%)**뿐이었습니다.
아래는 그 까닭입니다.

캐시는 **앞머리가 글자 단위로 같아야** 걸리고, 최소 **1,024토큰**이 필요합니다.

**측정한 것:** 모든 프롬프트가 **첫 7~18자 만에 변수로 들어갑니다.**
고정 지시문은 반대로 **꼬리**에 있습니다 — `master` 958자 · `draftPart` 501자 · `draft` 1,365자가
마지막 변수 뒤에 놓여 있습니다. 앞에 남는 고정 글자는 developer 메시지 450자(≈280토큰)뿐이라
**1,024토큰에 못 미칩니다.**

**순서를 뒤집으면** 지금 있는 글자만으로 앞머리가 만들어집니다.

| | 지금 앞머리 | 고정 지시문을 앞으로 옮기면 |

**얼마나 주는가.** `draftPart` 묶음마다 약 7,800토큰이 캐시로 넘어가면 입력 단가가 1/10이 됩니다 —

## 8. 실측하는 법 — 질의 두 줄

제 계정으로는 Cloudflare 인증이 안 됩니다(`code: 7403`). 터미널에서 실행해 주십시오.

**자리별 평균**

```
npx wrangler d1 execute ms12-proposal-archive --remote --command "SELECT task, COUNT(*) n, AVG(input_tokens) in_avg, AVG(cached_input_tokens) cache_avg, AVG(output_tokens) out_avg, AVG(reasoning_tokens) reason_avg, AVG(input_tokens*5.0/1000000 + output_tokens*30.0/1000000)*1400 won_avg FROM ai_usage_events GROUP BY task ORDER BY won_avg DESC"
```

**계획서 한 편별 합계**

```
npx wrangler d1 execute ms12-proposal-archive --remote --command "SELECT proposal_id, COUNT(*) calls, SUM(input_tokens) inp, SUM(cached_input_tokens) cached, SUM(output_tokens) outp, SUM(input_tokens*5.0/1000000 + output_tokens*30.0/1000000)*1400 won FROM ai_usage_events WHERE proposal_id != '' GROUP BY proposal_id ORDER BY won DESC LIMIT 20"
```

두 질의의 `cache_avg`·`cached`가 0에 가까우면 §5의 「캐싱이 안 걸린다」가 실측으로 확인됩니다.
`cost_micro`를 쓰지 않고 토큰에서 직접 셈하게 했습니다 — 2026-08-19 이전 기록은 비용이 0으로 남아 있어서입니다.
