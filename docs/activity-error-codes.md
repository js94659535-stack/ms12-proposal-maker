# 활동 기록의 오류 분류를 넓히는 안

운영 기록에서 오류 23건 가운데 21건이 `unknown`이었다. 어느 단계에서 멈췄는지는 알지만
**왜 멈췄는지는 모르는 상태**다. 3단계에서 한 사람이 같은 오류를 다섯 번 겪었는데 원인을 알 수 없다.

이 문서는 원인을 찾고 분류를 넓히는 안이다. **아직 고치지 않았다.**

---

## 1. CODE 정규식은 무고하다

`server/activity.js`

```js
const CODE = /^[a-z0-9][a-z0-9:_-]{0,39}$/;
code: CODE.test(text) ? text : 'unknown'
```

소문자·숫자와 `:` `_` `-` 만, 40자까지 받는다. **문장이 들어올 자리를 아예 두지 않으려는 장치**이며 그 목적은 제대로 하고 있다.

그런데 화면이 보내는 값은 이미 `unknown`·`file:extract`·`server:502` 같은 짧은 코드다. **전부 이 정규식을 통과한다.** 즉 서버에서 `unknown`으로 떨어지는 것이 아니라, **화면이 `unknown`을 만들어 보낸다.**

문제는 `src/activity.js`의 `errorCode()`다.

```js
for (const [pattern, code] of RULES) if (pattern.test(text)) return code;
return 'unknown';
```

규칙 10개 중 하나도 맞지 않으면 `unknown`. 서버는 그 값을 그대로 받아 적을 뿐이다.

> **고칠 자리는 `server/activity.js`가 아니라 `src/activity.js`다.**
> 서버의 CODE 정규식은 그대로 두는 것이 맞다. 문장이 서버에 닿지 못하게 막는 마지막 벽이다.

---

## 2. 실제로 무엇이 unknown이 되는가

`src/app.js`가 실제로 띄우는 오류 문구를 모아 `errorCode()`에 넣어 보았다.

| | |
|---|---|
| 화면 오류 문구 | **128종** |
| 분류됨 | **17종 (13%)** |
| **unknown** | **111종 (87%)** |

분류되는 17종의 내역은 `file:extract` 8 · `network` 4 · `archive:save` 4 · `ai:timeout` 1 이다.
**`auth:*` 4종과 `input:too-large`, `ai:config` 규칙은 실제로 걸리는 문구가 하나도 없다.** 규칙이 상상으로 만들어졌고 실제 문구와 맞춰본 적이 없다는 뜻이다.

unknown 문구에 자주 나오는 낱말:

```
주세요(48)  못했습니다(27)  없습니다(25)  먼저(17)  계획서(14)
찾지(13)  입력해(12)  다시(9)  적어(9)  선택해(8)
```

### 여기서 드러난 것 — 절반은 오류가 아니다

unknown 111종을 읽어 보면 성격이 뚜렷이 갈린다.

**(가) 입력 안내 — 약 48종.** 사용자가 아직 하지 않은 일을 알려 주는 말이다.

```
· 요청 사업명을 적어 주세요.
· 먼저 신청기관을 고르세요.
· 수정 요청 내용을 적어 주세요.
· 공고문을 30자 이상 붙여넣어 주세요.
· 이메일과 비밀번호를 입력해 주세요.
```

**이것은 실패가 아니다.** 폼을 덜 채우고 버튼을 누른 것뿐이다. 그런데 지금은 `error` 이벤트로 기록되어, 진짜 오류와 같은 통계에 섞인다. 앞서 본 21건의 `unknown` 중 상당수가 여기일 가능성이 높다.

**(나) 선행 조건 없음 — 약 35종.** 앞 단계를 하지 않아 이번 작업을 할 수 없는 상태.

```
· 검증할 계획서가 없습니다.
· 확정값을 반영할 계획서 본문이 없습니다.
· 계획서에 「사업 필요성」 항목이 없습니다.
· 공고 실행계약서가 없어 재설계할 수 없습니다.
· 이 보관 계획서에는 사용할 본문이 없습니다.
```

이것도 실패가 아니라 **순서 문제**다. 다만 (가)와 달리 「어느 단계를 건너뛰었는가」를 말해 주므로, 흐름 설계를 고칠 실마리가 된다.

**(다) 진짜 실패 — 약 28종.** 하려던 일이 안 된 것.

```
· 처리하지 못했습니다.
· 요청을 처리하지 못했습니다.
· 신청기관 정보를 삭제하지 못했습니다.
· 확정값을 반영할 문단을 찾지 못했습니다.
```

**여기가 우리가 알고 싶었던 것인데, 지금은 (가)·(나)에 파묻혀 보이지 않는다.**

## 3. 안 — 세 걸음

### 걸음 1. 종류를 나눈다 (가장 큰 효과)

`error` 하나로 뭉뚱그리지 말고 셋으로 나눈다.

| kind | 뜻 | 예 |
|---|---|---|
| `guide` | 아직 안 한 일을 알려 준 것 | "먼저 신청기관을 고르세요" |
| `blocked` | 앞 단계가 없어 못 하는 것 | "검증할 계획서가 없습니다" |
| `error` | 하려던 일이 실패한 것 | "처리하지 못했습니다" |

이것만으로 **오류 통계에서 소음 70%가 빠진다.** 남는 것이 진짜 봐야 할 것이다.

`guide`는 그 자체로도 쓸모가 있다 — 어느 칸을 자주 비우고 누르는지가 보이면 그 화면이 무엇을 설명하지 못하는지 알 수 있다.

> **DB 변경이 필요하다.** `migrations/0006_operator.sql`의
> `CHECK (kind IN ('step', 'error'))` 때문에 새 kind가 들어가지 않는다.
> 마이그레이션으로 CHECK를 넓혀야 한다. (SQLite는 CHECK 수정에 표 재생성이 필요하므로,
> 대안으로 kind는 `error`로 두고 코드 앞머리를 `guide:`·`blocked:`로 나누는 방법도 있다.
> **이쪽이 훨씬 싸고 안전하다 — 표를 건드리지 않는다. 이 방법을 권한다.**)

### 걸음 2. 규칙을 실제 문구에 맞춰 다시 쓴다

지금 규칙은 실제 문구와 맞춰본 적이 없다(`auth:*` 4종이 한 번도 안 걸린다). 실제 128종을 기준으로 다시 만든다.

```js
const RULES = [
  // 아직 안 한 일 — 실패가 아니다
  [/(적어|입력해|붙여넣어|골라|고르세요|선택해)\s*주세요|고르세요|선택해 주세요/, 'guide:input'],
  [/(30자|자 이상|이상 입력)/, 'guide:too-short'],

  // 앞 단계가 없다
  [/계획서가 없|본문이 없|계획서를 먼저|먼저 계획서/, 'blocked:no-proposal'],
  [/신청기관을 먼저|신청기관을 선택|신청기관이 없/, 'blocked:no-applicant'],
  [/공고(문|가|를)?\s*(없|먼저)/, 'blocked:no-notice'],
  [/서식|실행계약서가 없/, 'blocked:no-form'],
  [/찾지 못했습니다|찾을 수 없/, 'blocked:not-found'],

  // 진짜 실패
  [/저장하지 못|보관함/, 'fail:save'],
  [/삭제하지 못/, 'fail:delete'],
  [/만들지 못|출력하지 못|내려받지 못/, 'fail:export'],
  [/파일|추출|변환/, 'fail:file'],
  [/처리하지 못|반영하지 못/, 'fail:apply'],

  // 바깥 원인
  [/시간이 (너무 )?오래|초과|timeout/i, 'ai:timeout'],
  [/보내지 못했|연결할 수 없|네트워크/, 'net:offline'],
  [/한도|용량|너무 (깁니다|큽니다|많습니다)/, 'limit:size']
];
```

순서가 중요하다. **「~해 주세요」를 먼저 걸러야** 그 아래 규칙이 안내 문구를 실패로 잘못 집지 않는다.

### 걸음 3. 규칙이 못 맞힌 것도 어디서 났는지는 남긴다 ★

규칙은 문구가 바뀌면 조용히 깨진다. 오늘만 해도 화면 문구를 여럿 고쳤다.
그래서 **규칙과 무관하게, 오류가 난 자리를 함께 남긴다.**

```js
// 지금
export const reportError = (step, message) => reportActivity('error', step, errorCode(message));

// 안
export const reportError = (step, message, origin = '') =>
  reportActivity('error', step, errorCode(message), origin);
```

`origin`은 **한글이 아니라 함수 이름 같은 짧은 영문 식별자**다. `runSimpleGeneration`, `exportFinalPackage`, `saveApplicant` 처럼.

- 원문이 아니다 → 개인정보가 실릴 수 없다
- 이미 있는 CODE 정규식(`^[a-z0-9][a-z0-9:_-]{0,39}$`)을 그대로 통과한다
- 코드가 `unknown`이어도 **어느 함수에서 났는지는 안다**

가장 싼 구현: `setState`에서 부를 때 호출 지점을 넘긴다.

```js
// src/app.js:3180
if (patch.error) void reportError(state.step, patch.error, patch.errorFrom || '');
```

`errorFrom`은 선택 항목이다. 중요한 자리(AI 호출·파일·저장·출력) 20곳쯤에만 붙여도 충분하다.
나머지는 빈 값이고 지금과 똑같이 동작한다.

## 4. 개인정보를 계속 안 남기는 방법

지금 설계의 원칙 — **원문을 보내지 않고 미리 정한 코드만 보낸다** — 은 옳다. 그대로 둔다.

넓히면서 지킬 것 셋:

1. **코드는 여전히 유한한 목록에서만 나온다.** 규칙표에 없는 값은 만들지 않는다. `origin`도 미리 정한 함수 이름 목록으로만 받는다(자유 문자열 금지).
2. **서버의 CODE 정규식을 완화하지 않는다.** 한글·공백·따옴표가 들어갈 수 없는 지금 형태를 유지한다. 이것이 실수로 문장을 보내더라도 막아 주는 마지막 벽이다.
3. **길이 상한(40자)을 늘리지 않는다.** 코드가 40자를 넘어야 한다면 그것은 코드가 아니라 문장이다.

추가로 권하는 것:

4. **`origin` 목록을 코드에 상수로 둔다.** `const ORIGINS = new Set([...])` 로 두고 목록에 없으면 빈 값으로 떨어뜨린다. 그러면 나중에 누가 `origin`에 사용자 입력을 넘기는 실수를 해도 새어 나가지 않는다.

## 5. 무엇부터 하면 되는가

| 순서 | 할 일 | 드는 품 | 얻는 것 |
|---|---|---|---|
| 1 | 규칙표를 실제 128종에 맞춰 다시 쓰고 `guide:`·`blocked:`·`fail:` 로 나눈다 | 한 파일, 반나절 | **오류 통계에서 소음 70% 제거** |
| 2 | `origin` 넘기기 — 중요한 20곳 | 반나절 | 코드가 unknown이어도 자리를 안다 |
| 3 | 운영관리자 화면에 코드별 집계 추가 | 하루 | 매주 보고 고칠 곳을 정한다 |

1번만 해도 다음 주에는 **"3단계에서 다섯 번 났다"가 "3단계에서 설계도 저장이 다섯 번 실패했다"로 바뀐다.**

## 확인해야 할 것

- 지금 운영 기록 31건은 **표본이 너무 작다**(사용자 10명, 6일). 위 비율은 화면 문구 128종을 기준으로 계산한 것이고, 실제 사용자가 어느 문구를 자주 만나는지는 다르다. 규칙을 넓힌 뒤 2~3주 더 모아 보고 판단하는 것이 맞다.
- `MAX_EVENTS_PER_USER = 40`이라 오래된 기록은 지워진다. 분류를 넓히면 `guide`가 늘어 **진짜 오류가 40건 밖으로 밀려날 수 있다.** kind별로 상한을 따로 두거나, `guide`는 상한을 낮게 잡는 것을 함께 검토해야 한다.
