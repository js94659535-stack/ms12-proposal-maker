# 공고 수집 다음 단계 (조사 결과와 권장안)

2026-08-11 조사. **이 문서는 제안이다. 여기 적힌 자동수집과 새 출처는 아직 만들지 않았다.**

## 0. 지금 상태

`functions/api/notices.js`가 사람이 「공고 가져오기」를 누를 때만 돈다. 출처 두 곳 × 통로 두 개 = 네 갈래를 각각 돌리고 실패를 따로 알린다. 확인된 목록일 때만 D1 `archived_notices`에 넣는다.

측정값(2026-08-11): 중앙회 포털 10건 · 중앙회 공지사항 3건 · 광주지회 포털 6건 · 광주지회 공지사항 0건 = **19건**, 7.2초.

한계는 하나다. **아무도 버튼을 누르지 않으면 새 공고가 들어오지 않는다.** 2026-06-26부터 2026-08-11까지 수집이 0건이었는데도 검색은 잘 되어 아무도 눈치채지 못했다.

## 1. 자동수집: 하루 두 번이면 충분하다

접수기간이 보통 2~4주다. 하루 두 번(예: 08:00·18:00 KST)이면 반나절 안에 새 공고를 잡는다. 시간마다 돌 이유가 없고, 공식 사이트에 부담만 준다.

```
0 23,9 * * *   # UTC. 한국시간 08:00 / 18:00
```

## 2. Pages냐 별도 Worker냐 — **별도 Worker Cron**

| | Pages Functions | 별도 Worker |
|---|---|---|
| Cron Trigger | **지원하지 않음** | 지원 |
| 같은 D1 붙이기 | 지금 `ARCHIVE_DB` | `database_id`를 같게 적으면 같은 DB |
| 배포 | main push와 함께 | 따로 `wrangler deploy` |

Pages Functions에는 예약 실행이 없다. **`wrangler.toml`에 두 번째 Worker를 두고 `[triggers] crons`를 붙이는 것이 유일하게 곧은 길이다.** 수집 로직은 이미 `server/notice-collect.js`(통신 없는 규칙)와 `functions/api/notices.js`(통신)로 갈라 두었으니, Worker는 목록 발급 함수만 불러 쓰고 사람이 누르는 경로와 코드를 공유하면 된다.

권장 범위:

1. `workers/collect/index.js` — `scheduled()` 안에서 목록 발급 → `syncable`일 때만 `syncNotices()`.
2. `wrangler.toml`에 Worker 하나 추가(같은 D1, 같은 `ARCHIVE_DB` 바인딩).
3. 수집 결과를 새 표 `notice_collect_runs`에 한 줄씩 남긴다(아래 3번).
4. 사람이 누르는 「공고 가져오기」는 그대로 둔다. 자동수집이 멎어도 손으로 받을 수 있어야 한다.

예상 작업량: 반나절. 예상 비용: **하루 2회 × 6요청 = 월 약 360회.** Workers 무료 한도(하루 10만 요청) 안이고 D1 쓰기도 수십 건이라 사실상 0원이다.

## 3. 수집 상태판 (관리자 화면)

지금 실패는 화면에 한 번 뜨고 사라진다. 남겨야 볼 수 있다.

새 표 하나면 된다(추가만 하는 마이그레이션).

```sql
CREATE TABLE notice_collect_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  started_at TEXT NOT NULL,
  trigger TEXT NOT NULL,          -- 'cron' | 'manual'
  source TEXT NOT NULL,           -- central | gwangju
  channel TEXT NOT NULL,          -- proposal | board
  status TEXT NOT NULL,           -- ok | failed
  reason TEXT NOT NULL DEFAULT '',
  listed INTEGER NOT NULL DEFAULT 0,
  candidates INTEGER NOT NULL DEFAULT 0,
  collected INTEGER NOT NULL DEFAULT 0,
  inserted INTEGER NOT NULL DEFAULT 0
);
```

관리자 화면에 보여 줄 것 세 가지만:

- **마지막 성공 시각** — 통로별로. 「중앙회 포털 3시간 전 · 광주 공지사항 2일 전」
- **연속 실패** — 2회 이상이면 눈에 띄게.
- **0건 급감** — 최근 7회 평균 대비 절반 아래면 경고. 이번 장애처럼 「성공했는데 0건」인 상태를 잡는 유일한 신호다.

지어낸 지표를 넣지 말고 이 세 개만. 알림은 이메일보다 화면 배지가 먼저다(운영자 계정이 아직 없다).

①②는 지금 사랑의열매와 같은 eGov `.do` 구조라 기존 코드 모양을 그대로 쓴다. ③은 크롤링이 아니라 계약된 API라 화면이 바뀌어도 깨지지 않는다. robots가 막는 곳(아동권리보장원 공지, 삼성꿈장학재단, 보조금24)은 **넣지 않는다.**

### 이용조건·중복·비용

- **이용조건**: 위 표의 robots를 지킨다. 요청은 하루 2회, 출처당 동시 3건 이하로 지금 규칙을 그대로 쓴다. 공고 원문은 저장하되 **재배포하지 않고 원문 주소를 함께 보관**한다(`source_url`은 이미 채우고 있다).
- **중복**: 지금 규칙을 그대로 넓히면 된다. ①같은 출처 안에서는 `source:listSn`, ②출처가 달라도 **같은 기관·같은 제목(띄어쓰기·괄호 무시)** 이면 하나로 본다. 새 출처가 늘면 「기관이 다른데 같은 공고」(중앙회 공고를 지자체가 다시 올리는 경우)가 생기므로, 제목+마감일이 같으면 묶고 **먼저 들어온 쪽을 대표로** 두는 규칙을 하나 더 넣는다.
- **예상 운영비**: 출처 3곳을 더해도 하루 2회 × 약 20요청 = 월 1,200회. Workers·D1 무료 한도 안이다. **AI를 부르지 않으므로 OpenAI 비용은 0원.** 늘어나는 것은 D1 저장공간뿐이고 공고 한 건이 2~4KB라 연 1,000건이어도 4MB다.

## 5. 한 곳이 멈춰도 전체가 멈추지 않게

이번 작업에서 절반은 이미 했다. `CHANNELS` 배열에 통로를 등록하고 `runChannel()`이 각각을 감싸므로, 한 통로가 던져도 나머지는 돈다.

새 출처를 붙일 때 지킬 것:

1. **출처 하나 = 등록표 한 줄.** `functions/api/notices.js`의 `SOURCES`·`CHANNELS`처럼 자료로 두고, 코드 분기를 늘리지 않는다.
2. **판정은 통신 없는 모듈에.** `server/notice-collect.js`처럼 파서·상태 판정을 따로 두면 새 출처마다 시험을 붙일 수 있다.
3. **실패는 값으로 돌려준다.** 던져서 전체를 멈추지 말고 `{status:'failed', reason}`으로.
4. **출처별 스위치.** 한 곳이 오래 깨져 있으면 관리자가 그 출처만 끌 수 있어야 한다(`enabled` 열 하나).
5. **0건은 실패가 아니다. 그러나 0건이 계속되면 경고다.** 3번 상태판이 이 경계를 본다.
